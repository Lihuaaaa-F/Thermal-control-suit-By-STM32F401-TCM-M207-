  故障记录器缺陷的根因与修复（03:30–03:43，集成分支提交见 git log："HardFault 入口改成 naked 汇编…"）
  追查过程：先给记录加字段（栈指针、栈内的 LR / xPSR、ICSR、SHCSR、FPCCR、序号），再触发三次（注入 0x08000000 / 0x60000001 / 0x00000001）。
    三次的栈内 LR、xPSR、SP 一模一样（0x08007BFB / 0x2000081C / 0x2001FC20），可三个注入地址引起的故障完全不同——
    说明这几个字根本不是硬件压进去的现场，是别处残留的数据。EXC_RETURN=0xFFFFFFE9 的含义是"回到线程模式、用 MSP、扩展帧"。
  根因：本工程没有 RTOS，主循环用的就是 MSP；异常进入时硬件把被打断的现场压在 MSP 上。原处理函数是普通 C 函数，
    一进来先 push 寄存器，之后才去读 MSP——读到的已经是压过寄存器的位置，于是记下的是处理函数自己压进去的东西。
    （它按 EXC_RETURN 的 bit2 分 MSP / PSP 两条路，走的正是 MSP 那条。）
  修法：入口改成 naked 汇编——先取 SP 与 EXC_RETURN，再尾调用 C 函数 hardfault_c(frame, lr)；记录逻辑不变，多留上面那几个字段和序号；
    新增只读命令 fault，随时可以重打记录（原来只在上电时打进 RTT，事后读不到）。
  修后同一套触发（判别性证据）：
    注入 0x08000000 → PC=0x08000000（= 注入地址）stk_lr=0x0800A687（out_tec_sw 的调用者）xPSR=0x60000000（T 位=0：试图切到 ARM 态）
                      CFSR=0x00020000（UNALIGNED）HFSR=0x40000000 SP=0x2001FC50 seq=1；固件自己的打印与探针读的一致
    注入 0x60000001 → PC=0x60000000（= 注入地址，最低位是 Thumb 位）xPSR=0x610B0000（T 位=1）CFSR=0x00000100（IBUSERR）seq=2
    注入 0x00000001 → 跳到地址 0 去执行（那是向量表，当指令执行是随机行为）：这一次没有复位、记录没有更新、屏没把急停发出去、
                      邮箱也不再应答——执行垃圾代码后的不确定结果，不属于记录器的问题，如实记下。
    每次触发后板子都在约 2 秒后自行复位并恢复运行；主控随即进入急停态（fan=100% alarm=0x0004 state=3），ack 后回零。
