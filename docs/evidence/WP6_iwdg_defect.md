# WP6 缺陷报告：IWDG 喂狗间歇失效（未结案，硬件联调日优先排查）

**状态**：未结案。当前发布配置 RLR=4095（32.7s，GS 工程同款已证值）规避 2s 档复位循环；
任务书 §3.9 "~2s" 的 RLR=249 已备好（`App/iwdg/iwdg.c` 注释内），根因定位后一键切回。
**影响**：F5 死机自恢复窗口从 2s 放大到 32.7s（功能仍在，窗口变宽）；其余全部功能不受影响。

## 现象（多源实证）

1. IWDG=2s（RLR=249）时：上电稳定复现复位，周期 ≈2.85s（= 2.0s 看门狗 + ~0.85s 启动）。
2. IWDG=32.7s（RLR=4095）时：单会话 40s 追踪 uwTick 完美 1:1 增长（4938→32964ms，
   每采样 +2002ms/2s），31.7s 处发生一次复位；另组观测到 76s 长跑。
3. 复位源寄存器 RSR=0x04460000：bit26 **IWDG1RSTF** 置位（bit22 PINRSTF 为 H7 内部复位
   外驱 NRST 的伴随位）——**复位确为 IWDG**。首版控制台解码把 PIN 判在前面，一度误判。
4. 主循环持续运行的证据：AXI SRAM 相位轨迹 12s×1501 次采样 100% phase=12（完整循环）；
   PC 高频采样数千次全部落在 main.c:558 节拍等待；uwTick 1kHz 完美走时。

## 已系统性排除（每项有实证）

| # | 假设 | 排除依据 |
|---|---|---|
| 1 | 串口线序扰动 NRST（CH340X 自动下载电路） | 真实存在（见附录 B），但**串口全关、仅 DAP 空闲连接**下复位仍发生 |
| 2 | DMA2D TC 忙等死等 | 已捕获一次现场并加固（超时+软复位+空矩形防御）；加固后现象不变 |
| 3 | 代码停顿/死循环 | 数千次 PC 采样 + 相位直方图 100% 正常；IWDG 触发需 >2s 连续停顿，从未捕获 |
| 4 | SysTick/时基停摆 | uwTick 与墙钟 1:1（+2002ms/2s）；PRIMASK=0；SysTick CTRL ENABLE/TICKINT=1 |
| 5 | 链接/编译错位 | `probe-rs verify` Flash==elf ✓；`bl iwdg_refresh` 在 main 反汇编中 ✓；control_poll 反汇编逐指令核对 ✓ |
| 6 | 喂狗地址/指令错误 | IWDG1_BASE=0x58004800 与 CMSIS 一致；反汇编 `str 0xAAAA,[0x58004800]` ✓ |
| 7 | 中断关闭 | PRIMASK=0，SysTick 中断持续服务 |

## 矛盾点（待解）

循环每拍执行正确的喂狗指令（反汇编+相位轨迹证明），但 IWDG 仍按超时复位——
即喂狗写**在执行却未生效**。剩余假设：
- A. 周期性总线/电源微故障使该 str 丢失（供电经 DAPLink USB，LCD 背光同轨）；
- B. 某运行路径改写 IWDG 寄存器（需数据断点验证）；
- C. pyocd/probe-rs 附加会话本身对总线的扰动使喂狗丢失（但静置期不接调试器的
  复位循环已由串口日志侧面观察到，与 A 相互印证）。

## 建议排查步骤（硬件联调日，预计 30 分钟）

1. 外部 5V 独立供电（脱开 DAPLink 供电轨），串口日志观察是否仍 2.85s 复位；
2. pyocd `target.write_watchpoint(0x58004800)` 数据断点：确认喂狗写是否到达；
3. 若写到达仍复位：读 IWDG->RLR/PR 运行时值是否被改；
4. 复现后按 embedded-dev-loop §4 格式记录并更新本文件。

## 附录 A：关键测量记录

- 复位周期（IWDG=2s）：uwTick 锯齿 + 相位法多轮实测 ≈2.85s
- IWDG=32.7s：单会话 uwTick 4938→32964（+2002ms/2.000s）后单次复位（≈34s 处）
- 不接调试器长跑：RTT/串口仅能捕获启动段，长跑表现见 76s 记录

## 附录 B：COM4/CH340X 自动下载电路行为（板级已知问题）

- 串口打开瞬间 + DTR/RTS 电平变化 → NRST 脉冲（板复位）
- 复位瞬间 BOOT0 采样由 DTR/RTS 线序决定：DTR=True → Flash 启动；False → ROM
  bootloader（0x1FF09800，表现为"串口死+外设寄存器读 0"）
- 规避：先关串口复位→再开串口；或割断自动下载电路跳线；或改用独立 USB-TTL 接控制台
- 证据：DTR=False 时 probe-rs 复位后 PC=0x1FF0A4C0（ROM）；DTR=True 时 PC=0x080053EE
  （Flash 主循环）；串口关闭时复位后 PC 恒在 Flash

## 续篇 2026-10-18：USB 口供电对照实测（总设计师复测）

**实验条件**：供电从 COM 口（CH340 同轨）换到板上原生 USB 口；COM 口未插；DAPLink 仅在读取瞬间附加（-M attach，实测不触发复位——attach 前后 uwTick 连续可证）；RLR=4095（32.7s 档）。

**数据**：
- 上电后 uwTick 15946ms → (+3s 实墙钟) 19993ms：节拍 1:1，板子正常运行
- (+35s 窗口，无调试器) uwTick=6654ms → 窗口内发生复位
- (+40s 窗口，无调试器) uwTick=13974ms → 再一次复位；本轮存活 ≈33.7s ≈ 32.7s 超时+启动开销
- 运行时 IWDG RLR=0x0FFF、SR=0；RCC->RSR=0（固件启动清标志，无法事后判源，以周期指纹为准）

**结论（假设收敛）**：
1. ✅ 排除：CH340/COM 口供电轨（换 USB 口仍复现）
2. ✅ 排除：调试器附加扰动（无调试器窗口复位照发）
3. ➖ 减弱：IWDG 寄存器运行中被改写（RLR 实时读回完好）
4. ⏳ 剩余主嫌疑：喂狗写"在执行但未生效"的深层机制（D3 域/APB4 总线访问间歇丢失、LSI/时钟域异常），或存在未被采样的长停顿

**下一步（T1.1 升级版）**：BKP 备份寄存器仪表固件——记录复位次数、每次复位的 uptime、复位前最后一次喂狗的 uwTick 时刻、RSR 快照；复位后自证"最后喂狗距今 Δt"。Δt<1s → 喂狗写失效实锤；Δt>30s → 间歇长停顿（与既有轨迹证据矛盾，需重审）。

## 续篇补 2026-10-18：DAPLink 硬件在位 = 新头号嫌疑（用户关键观察）

**用户观察**：USB 口供电下屏幕一直黑；拔掉 DAPLink 后**屏幕立即点亮**。

**修正归因**：前述"无调试器窗口复位照发"的窗口里，拔掉的只是 pyocd 会话，**DAPLink 硬件始终在位**（COM8 一直枚举）。因此"调试器扰动排除"不成立，应改为：**调试会话排除、DAPLink 硬件在位反而被指认**。

**统一假说（待 A/B 验证）**：DAPLink 的 3.3V/SWD 与板上电源倒灌争抢，3.3V 轨被拖低——大电流负载（背光）带不动=黑屏；MCU 低电流可跑=uwTick 跳动；喂狗写经受污染总线间歇丢失=IWDG 复位（RSR 指认 IWDG 与此相容）。该假说同时解释历史全部实验（agent 时代 DAPLink 常插）与今日现象。

**判决性 A/B（人工 3 分钟）**：① DAPLink 保持拔出，看屏 2-3 分钟无重启重画 → 基线干净；② 现场插回 DAPLink（不动其它线）→ 若屏幕变黑/开始周期重画 → 因果实锤；③ 拔出 → 恢复 → 复现性确认。
**注意**：若假说成立，工作流改为"DAPLink 只在烧录瞬间插入，运行观测走屏幕/串口"；T1.1 BKP 仪表固件需把复位计数/uptime 显示到屏幕角落（DAPLink 拔出时代的人读仪表）。

## 结案 2026-10-18：根因 = HAL_IncTick 覆写丢失，g_tick_ms 恒 0，主循环首圈卡死在节拍忙等

**侦破链**：黑匣子固件（SysTick ISR 喂狗实验臂）上线后 33s 复位消失 → loop_passes=1 纹丝不动 vs uwTick 满速走 → halt 抓 PC=main.c:564（`while (g_tick_ms - last_tick < 10u)`）→ grep 全工程 g_tick_ms 无任何递增点 → GS 工程原有 `HAL_IncTick(){uwTick++;g_tick_ms++;}` 覆写在移植重写 main.c 时丢失。

**完整因果**：g_tick_ms≡0 → 主循环第一圈完成即卡死在节拍等待 → 无喂狗 → IWDG 复位（2s 档周期 2.85s / 32.7s 档周期 33.7s，全部实测吻合）→ 重启再死循环。SysTick/uwTick 一直正常 → 此前所有"系统在跑"的观测（uwTick 墙钟比对、屏幕静态页、boot 日志）全部与卡死相容——观测指标选错导致长期误判"喂狗失效"。

**修复**：main.c 恢复 HAL_IncTick 双递增覆写。修复后实测：g_tick_ms 3270→9082ms，loop_passes 283→812（≈106Hz 满速），主循环健康。

**附带工具链坑（全部入档，防再踩）**：
1. pyocd cmd 会话退出可能留核于 HALT（DHCSR=0x30003），核停期间 IWDG 被 DBGMCU 冻结连复位都不发生——用 pyocd 后必须查 DHCSR；
2. probe-rs 0.32：`read b32 <ADDR> <WORDS>`（WORDS 必填）、RTT=子命令 `attach`、`download` 后不保证复位运行——烧后必须显式 `probe-rs reset`；
3. 本板（旧版 CMSIS 头+现有硅片）BKP 备份寄存器在 DBP/RTCAPBEN/WPR 解锁/RTCEN 全开下仍不可写——黑匣子持久化后续改 DTCM .noinit 段或随 T1 结案移除；
4. 改 main.c 重链接后 bss 地址漂移——调试读取必须每次从新 ELF 重取符号地址。
