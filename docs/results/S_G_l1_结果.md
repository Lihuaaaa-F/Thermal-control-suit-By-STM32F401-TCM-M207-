## 2. R5-01 专项证据

### 2.1 设计（与说明的建议同向，两处按实际代码调整）

| 说明里的设计要求 | 实际做法 |
|---|---|
| 协议在字节层面能回答"这帧是谁发的"；优先用帧层现成的空闲位 | 用消息号字节的 **bit6**：在用的消息号（TCS 与 GS 遗留）bit6 全是 0，`_Static_assert` 钉死"消息号不得占用 bit6"。一个机制对所有消息号生效，不靠逐个消息号改 |
| 极性 | **1 = ESP32 发**。理由：只换一端时倒向安全的一侧——旧屏的帧没有这一位（读作 H743），新 ESP32 照常认，急停 0x15 / 写参数 0x12 仍执行；若定成"1 = H743"，旧屏的急停会被新 ESP32 当成"本端回送"丢掉 |
| 建议镜像改用专用消息号 | **没有新增消息号**，改法等价而更小：0x11 起只做 ESP32→H743 镜像；屏写参数一律走已经等 ACK 的 0x12（即 R5 复核报告 R5-10 的最小修复建议"屏→ESP32 的参数写入统一走等 ACK 的路径"）。ESP32 侧"收到 0x11 就写权威注册表"的代码路径**已不存在**——即使方向位被改坏，镜像回声（0x11）在 ESP32 也没有处理分支 |
| 丢弃必须发生在任何处理之前；只看字节，不看长度、不看时刻 | 闸门在两端 `comm.c` 的 `comm_rx_feed_byte` 里、ACK 分支 / 去重 / 交付之前。判定函数 `tcs_rx_verdict`：先看方向位（本端回送一律丢，含 ACK），再看方向表（对端不会发的消息号丢；ACK 确认的必须是本端会发的消息号） |
| `echo=` 语义保留并按消息号分计 | `linkstat`：`echo=`（总数）+ 第二行 `echo_by: 11= 13= 20+21= 22= 90=`；另加 `arq=`（comm 层 link_ok）、`wdir=`（方向表不允许的对端帧数）、`txwdir=`（本端发错方向的自检） |
| 等长 + 发送窗过滤删除 | `s_echo_plen` / `s_echo_until_ms` / `TCS_ECHO_MARGIN_MS` / `s_echo_drop` 全部删除；`proto_sync.py` 第 7 项核对零残留 |
| 协议唯一源 | 只改 `protocol/tcs_proto.h`；两端包装文件未动；`proto_sync.py --check` 通过 |
| `TCS_PROTO_VER` 是否递增 | **不递增**。理由：屏端 POST 的 VER 自检项写死 `TCS_PROTO_VER == 1`（`project_tcs/App/tcs/post.c:241`），递增会让交付档自检失败；屏端还按等值丢弃 `ver` 不符的快照。方向位的不兼容是整帧级的（不出数、不误写），靠"两端固件必须成对更新"约束（已写进头文件）。要递增须连同 POST 那一项一起改——**需要你决定** |
| 判定逻辑是不依赖 IDF / HAL / LVGL 的纯函数；两份 comm.c 不再漂移的办法 | 判定在唯一源头文件里；两份 `comm.c` 的闸门函数 `comm_rx_gate` 逐字相同，`proto_sync.py` 每次核对；两端各自的主机用例编译自己那一份；变异脚本对两份分别下变异体 |

只换一端的实际表现（已写进头文件，只为排障）：

| 组合 | 表现 |
|---|---|
| 新 ESP32 + 旧屏 | 旧屏不认带方向位的 0x20 → 屏不出数；旧屏用 0x11 写的非 M207 参数被按方向表丢弃（屏上改了又跳回）；ESP32 日志反复 `link down (ARQ)`（0x13 得不到 ACK） |
| 新屏 + 旧 ESP32 | 屏把旧 ESP32 的帧全当"本端回送"丢弃 → 屏不出数；屏的写参数 0x12 与急停 0x15 仍会到达旧 ESP32 并执行 |

| 0x21 | `MT_TCS_DELTA` | 仅 ESP32 | `esp32/main/tcs_snap.c:173`（ESP32）| `project_tcs/Core/Src/main.c:507`（H743）|
| 0x22 | `MT_TCS_INFO` | 仅 ESP32 | `esp32/components/tcs_link/link_task.c:510`（ESP32）| `project_tcs/Core/Src/main.c:502`（H743）|
| 0x90 | `MT_TCS_ACK` | 双向 | `esp32/components/tcs_link/link_task.c:342`（ESP32）<br>`project_tcs/Core/Src/main.c:298`（H743）| comm 层消费 |

0x15 的 ESP32→H743 方向当前没有调用者（`link_send_cmd` 零调用），但两端都有发送代码与接收分支，按"双向"登记。

门禁有牙的核对（在临时副本上造违规，逐条报出）：(a) 屏端复活 `case MT_TCS_SET_PARAM` → "H743 有接收分支，但方向表说 ESP32 不会发它"；(b) 主控用 0x12 发镜像 → "ESP32 在发，但方向表说 ESP32 不会发它"；(c) 主控端闸门挪到 ACK 之后 → "闸门调用点不在 ACK 处理之前"；(d) 改动一端闸门函数体 + 残留旧符号 → "两端 comm_rx_gate 不再逐字相同" + "仍有旧回声过滤的符号"。"把方向表放宽"（例如 0x11 改双向）源码门禁不报——它只管"代码与表不符"，表本身由屏端用例的方向表断言钉住（变异 D4 / D5）。

### 2.5 残余风险（如实）

方向闸门之后，一回声要被当成对端帧，需要同时满足：**回声被改坏、恰好过 CRC8、且方向位也被改坏**。逐类估算（p = 单个比特出错的概率，只在做账时用）：

| 回声类型 | 被当成对端帧之后会发生什么 | 还要满足什么 | 量级 |
|---|---|---|---|
| 参数镜像 0x11（事故路径：写权威注册表） | 无事发生——ESP32 已没有"0x11 写入"的分支 | 要被当成"屏的写入"，消息号字节还得从 `0x51` 被改成恰好 `0x11`（4 个特定比特同时翻）且过 CRC | 随机比特翻转：≈ `p^4 / 256`（p = 0.1 时 ≈ 2.6e-7 / 个坏回声）；消息号字节被整字节改写：≈ 1/65536。**修复前**：坏回声过 CRC（1/256）即写入，按镜像 1.25 帧/s 算，故障持续约 3.4 分钟一次 |
| 快照 0x20 / 增量 0x21 / 设备信息 0x22 | 屏用自己刚发的数据刷一遍显示（幂等）；方向表不允许的记入 `wdir=` | — | 无害 |
| 应答 0x90 | 可能清掉一帧等待确认的状态 | 方向位被改坏，**并且**它确认的消息号是本端会发的：本端发出的应答确认的只会是对端发来的消息号（0x12 / 0x13 / 0x11 / 0x20 …），按方向表过不了。唯一例外是双向消息号 0x15——当前该方向没有流量 | v2 下不可达 |

- **"协议只有 CRC8"另列遗留**：把校验换成 CRC-16 能把"坏帧过校验"的概率从 1/256 降到 1/65536，但要同时改两端 `proto.c`、Python 参考与所有字节向量，建议单独立项（可归 e1）。
- 方向位本身在 CRC 覆盖范围内：方向位被改而 CRC 仍对的概率就是 1/256，不是独立的一层。
- 接线根因（现场 O1）与 `tc1_set` 仍是 5.0（O3）不在本批次范围。

### 2.6 真机验证读数（你来跑；两端都必须是新固件）

条件同你的基线：ESP32 诊断档、芯片内回环 20 秒、H743 交付档。

开机日志：`[LPBK] RESULT pass=4 fail=0 PASS`（修复前每次开机都是 `pass=3 fail=1 FAIL`——第 4 项只数"交付"的份数，重传副本被去重后恒为 1；已在主机上复现并改为屏 / 主控两个实例共用一条回环线）。

`linkloop 1` 之前先记一组 `linkstat`，20 秒后再读，看**增量**：

| 字段 | 期望 | 说明 |
|---|---|---|
| `echo=` | +147 到约 +250 | = 回环期间本端发出的总帧数：快照 0x20 每 200ms 一帧 → 100；镜像 0x11 每 800ms → 25；设备信息 0x22 每 3.2s → 6～7；请求注册表 0x13 → 约 16（回环下收不到 ACK，每个请求周期发 4 帧）；增量 0x21 的数目取决于体温 / 设定 / 执行器状态变化有多频繁（0 到 100）。可与 `[SNAPP] … snap= delta=` 那行对账 |
| `echo_by:`（第二行）| `11=25 13≈16 20+21=100+Δ 22=6～7 90=0` | 按消息号分计 |
| `rx_f=` | **不变** | 回声一帧都不交付（你的基线：停在 395 不动） |
| `dup=` | **不变** | 你的基线是 +4（有 4 帧穿过旧过滤进了 comm 层）；现在应为 +0 |
| `retry=` | 增长（约 +12） | 回环下 0x13 得不到 ACK 的正常现象 |
| `arq=` | 1 → 0，并保持 0 | 请求注册表的 ARQ 耗尽；应答回声不会把它置真。`linkloop 0` 之后对端第一帧到达即回 1 |
| `wdir=`、`txwdir=` | 0 | `wdir` > 0 表示有 CRC 正确但方向表不允许的帧——接线 / 串扰劣化的信号，请把数记下来 |
| `crc=`、`len=`、`verg=` | 不变 | 完好的回声 CRC 正确 |
| 日志 | `self-echo on RX dropped=N`，N = 1、21、41… | 每 20 帧一条 |
| 日志 | 不出现 `PARAM id=`，也不出现 `H743 SET id=` | 前一行在 ESP32 代码里已不存在；后者只在屏真的发来 0x12 时才有 |
| `p list` | 回环前 / 中 / 后逐项一致 | |

**看到什么就算不通过**：回环期间出现 `H743 SET id=` 或参数值变化；`rx_f` 或 `dup` 增长；`echo=` 的增量明显小于同期发出的帧数（说明有帧没带方向位出去了——两端固件不成对）；`wdir=` 持续增长。
`linkloop 0` 之后快照应恢复；H743 的 `stat` 新增 `echo=` / `wdir=`，屏这一侧正常应恒为 0。

屏端另一条可看的：ESP32 上电到屏固件成对更新之后，屏 `stat` 的 `echo=` 应保持 0；若屏侧 `echo=` 增长，说明屏发往 ESP32 的那根线有回声。

## 4. 有风险、需要人看的点

1. **两端固件必须成对更新**，没有版本号兜底（`TCS_PROTO_VER` 未递增，理由见 §2.1）。只换一端时屏不出数，但不会误写、急停仍能到达旧 ESP32。要不要连同 POST 的 VER 项一起把版本号抬到 2，需要你定。
2. **ESP32 的发送节拍是每 100ms 一帧**（`comm_poll_tx` 只在 100ms 节拍里调）。屏写参数改走等 ACK 之后 ACK 帧会多 1 帧 / 次写入；现有流量约 6.5 帧/s，余量够，但屏上连续快按加减键时等待确认的槽（8 个）可能被占满——被逐出时会记 `evict=`，请在上机时留意这个计数。
3. **开机自环自测的口径变了**（两个实例共用一条回环线），第 4 项从"恒 FAIL"变为 PASS。修复前每次开机都打印 FAIL，现场记录里如果引用过这一行，需要知道那不是新出现的故障。
4. **`gap=` 这个计数不能当故障指标**：`comm.c`（M04-F-03）在"静默超过 50ms 后来的第一帧"上就 `proto_rx_reset` 并 +1，所以屏每 500ms 一帧的 STATUS 让它每 2 秒涨 4；仓库里已有的现场读数（`gap=11558`，每分钟 +120）正是这个来源。本批次没有改它（不在条目里），只在此说明，避免拿它做结论。
5. ESP32 的 `notify()` / `s_last_param` 目前没有任何调用者（`link_on_event` 零注册）。我把原先 0x11 分支里的这两步并进了 0x12 分支以保持行为等价；如果以后接上网页推送，0x12 分支会多推一次，届时请核对。
6. 研学卡（`docs/ref/研学卡_*.md`）与本结果文档都会在本批次后续提交里继续改；合并时这两类文件必然冲突。
