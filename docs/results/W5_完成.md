## 2 为什么这样改（官方依据+被否方案）

官方依据：门禁脚本本体=既有清单 v4 机器化审计机制（台账在案，探针双向验证 EXIT 1/0 已历史实证）；本 W 仅做"接入"——nightly.sh 的 step 函数是既有门禁框架（任一 step 失败→FAIL=1→exit 非零），audit 步复用该框架=透传语义与 ①-⑦ 步完全一致。chdir 锚定=册 §6 预案原文"脚本未接 python 参数则补绝对路径"的实现化（比在两个调用点各写 cd 更稳：单一事实源）。

被否方案：
1. ❌ 给脚本加 `--root` 参数由调用方传仓库根——两个调用点都要传对，错一处门禁静默失效；chdir 自锚定无此风险。
2. ❌ rtt_count 门禁放 nightly 而非 run_all——run_all 是纯 PC 快速反馈层（无板也跑），越早红越好；nightly 全程 10min+。

## 5 找茬记录（≥3）

1. **门禁上线即抓真违规（坐实修复）**：audit 首跑（绿态检验）exit=1，1 uncovered=G 线未提交工具 project_tcs/tools/g4_e04_tl9b.py 未登记清单——正是 SOP 要防的案例（新增文件未同 commit 登记）。处置：--update-manifest 登记入清单（簿记动作）；若 G 线后续改名/删除该文件，stale 行不阻断（退出码只看 missing+unclassified），风险受控。
2. **rtt_count 口径陷阱（坐实修复）**：计数若用 `grep -c` 按**文件**计数会漏（-c 每文件计 1 起）；必须 `grep -rn | wc -l` 按**行**计数。实测两口径（App+Core vs 全 project_tcs）均=14（定义行+13 调用行；无 tests 命中），门禁取 App+Core 口径（run_all cwd 自然域）。
3. **nightly 探针协议的"头部"歧义（排除+处置）**：册 §6 写"跑 nightly 头部"——nightly 全程含 10min 丢包注入+探针步骤，探针验证不应真跑全程；evidence 中调用口径=⑧ 步同款命令（step 展开后的原样），双向红绿即证该步行为，等价性成立（step 函数仅包 tee/FAIL 记账，不改命令语义）。
4. **清单 SOP 注释与 stale 噪声（排除）**：若无注释跳过机制，SOP 头 3 行会成 3 条 stale 噪声；已随机制一并落地（加头后复跑 exit=0 实证）。
