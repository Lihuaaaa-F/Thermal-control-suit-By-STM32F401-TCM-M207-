## 三、操作链完整披露（含事故与恢复）

1. 备份：整片 2MB 读回 `docs/evidence/g4_onboard_backup_20261029.bin`（md5 748f9f96…，向量 SP/PC 校验通过）。
2. 刷 W 固件 → **首刷健康启动**（§一全部证据在此取得）。
3. 执行控制台命令批（`ver`+`stat` 成功；随后 `p list`/`post` 批次）→ **固件 HardFault**：CFSR=0x00000401（IACCVIOL+IMPRECISERR）、HFSR=FORCED、故障捕获 PC≈0x20000000（DTCM 底）、ICSR VECTACTIVE=3；固件自带故障转储在 RTT 写入 "FAULT CFSR=… HFSR=…"（至 "HFSR=" 截断）。**登记为 F17（待查缺陷）**：根因未定——三大嫌疑：①混合工作区构建（W HEAD+G 线未提交 ltdc.c MPU/main.c/.ld）②探针反复 halt 与 IWDG 2s 的交互（每次内存操作 halt ~0.3-0.5s，密集操作累计可将"未喂狗"窗口推过 2s → 复位/边界态被捕获为伪故障）③真实软件缺陷（如函数指针表被踩）。**须在 G 线合入后的干净树、且用不频繁 halt 的调试协议下受控复现**。
4. 崩溃后多次重新刷写/复位：出现擦除态（重建 W 时一度两 bank 起始全 FF，FLASH_CR1 残留 PG|SER|MER）——**已用备份分扇区修复**：向量区与 0xA0000-0xC0000 扇区经逐块比对=G4 原样；中途 DAPLink 持续出现 "Command ID in response does not match"（HID 链路劣化），全镜像逐块验证因读数据不可靠而无法完成。
5. **当前板状态（诚实结论）**：Flash 头部与多个抽样扇区=G4 备份原样（向量 20020000/08000d5d 逐字匹配），但全镜像完整性未证完（探针不可靠）；恢复后的 G4 曾有 FAULT 痕迹（后查明为恢复不完整所致，重写后该区已比对通过）。
6. **停止硬件操作**：探针读数互相矛盾，继续操作=证据污染与风险；按"失败 2 次停"纪律停手。

## 六、教训（入 methodology）

1. **动板前先读后写**：本会话应先只读板上状态（环/符号扫描），确认基线健康再决定是否刷——我直接刷写是流程错误（尽管做了备份）。
2. **IWDG 固件 + 频繁 halt 调试互斥**：探针每次操作 halt 0.3-0.5s，密集操作可越过 2s 喂狗窗口；作业规程=单次操作后静默 ≥3s、批量读用单会话工具、不在喂狗关键窗口做长会话。
3. **DAPLink HID 链路劣化后的读数据不可信**（同地址两次读不同=必须判读失败而非采信）；出现 Command ID mismatch 连续 2 次即应停手请用户拔插。
4. 备份与恢复必须**逐块 verify** 到 PASS 才算完成；"Finished"回显在链路劣化时不可信。
