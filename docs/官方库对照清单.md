## 六、维护规则（承 v1，增补）

1. 新增驱动类代码前：先查 ESP-IDF 官方组件+espressif 组件库（检索记录留档），查无才自研，自研处留"查证记录"注释。
2. 单线 LED/传感器/触摸类：一律优先组件库；**禁止手搓 RMT 时序**（F1 教训）。
3. **软件 I2C bit-bang 是红线信号**：新代码禁止（F2/F3 都源于此）；存量两处按 F2（候选迁移）/F3（R4 删除）处置。
4. H743 侧"官方"=ST HAL+LVGL（官方 UI 库）；ESP32 侧=ESP-IDF+espressif 组件库。
5. 本清单随 R*n 关单更新；Q3 反抽查含本清单条目抽验。

## 七、机器化审计机制（v4 新增；消除"扫全了吗"疑虑的制度化答案）

完整性不靠口头保证，靠**可复跑的机器证明**：

1. **脚本**：`esp32/tools/official_lib_audit.py`——`find` 枚举四树全部源文件（当前 **135 个**，
   不靠记忆）、按 **25 类分类学**（该用官方库的固定类别，每类一条可复核正则）逐文件打标，
   输出 `docs/evidence/官方库审计_机器报告.md`。
2. **缺口报警**：`docs/审计文件清单.txt` 为已审计文件基准；脚本每次运行做 diff——
   **任何未入清单的新文件 → 报告点名 + 退出码 1**（已用探针文件双向验证：塞入报警/删除恢复）。
   加入 run_all/nightly 后成为常驻门禁（待接）。
3. **对抗性抽查协议**（Q3 同款精神）：任何人（含用户）**任点本库任一源文件**，执行者必须当场
   给出该文件的审计行（行数/官方组件/自研内容/判定/对应 F 项）；点漏一个 = 清单缺陷立案，
   记入本清单版本沿革。本报告 135 文件的逐文件分类命中行即为抽查底册。
4. **边界声明**：正则分类命中≠缺陷（如 snprintf 命中"字符串/格式化"属正常），命中只是
   **待人工判定的定位器**；判定结论以第一~四节的 F 项与逐文件表为准。新文件出现→脚本点名
   →人工判定→清单增补，闭环。
